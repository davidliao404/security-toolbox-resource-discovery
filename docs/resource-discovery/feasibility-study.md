# 互联网暴露面资源发现模块可行性研究

## 1. 背景与目标

“安全工具箱”当前定位为客户私有化部署的安全运营工具，承担内部 IT 环境扫描、巡检、验证和处置任务。互联网暴露面资源发现模块是在该基础上新增的被动资产发现能力，用于帮助内部 IT 人员不足、但安全要求较高的组织快速理解自身暴露在互联网上的资产和风险线索。

目标架构为：

```text
客户私有化安全工具箱
-> 自研公有云资源发现网关
-> 外部资产发现 SaaS
-> 聚合与归一化结果
-> 返回安全工具箱生成管理者报告和本地处置任务
```

第一版目标不是替代本地扫描，也不是提供云端攻击验证，而是提供“被动发现 + 管理者报告 + 本地处置入口”。

## 2. 目标客户

首批目标客户包括：

- 一般中小型企业：缺少专职安全团队，需要低门槛了解互联网暴露面。
- 香港非盈利组织：安全预算有限，但存在公众服务网站、邮件系统、远程办公入口等暴露资产。
- 非核心政府单位：需要定期掌握暴露资产和风险线索，但不适合在云端执行主动探测。
- 内部 IT 人员资源不足的组织：希望工具给出清晰摘要、优先级和处置建议。

共同特征是：管理者需要看得懂结论，IT 人员需要拿得到证据和任务。

## 3. 核心价值

模块的核心价值包括：

- **暴露面可见性**：让组织知道哪些域名、IP、端口、服务和入口暴露在互联网。
- **风险优先级**：把疑似远程访问、管理后台、测试环境、过期组件等线索转为管理者可读的优先级。
- **低操作成本**：客户只输入组织名、根域名、IP 段等基础信息，即可获得报告草稿。
- **证据链保留**：报告结论必须关联来源、发现时间、查询条件和原始证据引用。
- **本地闭环**：高风险线索回到私有化安全工具箱中，由客户本地执行验证、巡检和整改。

## 4. 外部 SaaS 可行性

外部资产发现 SaaS 适合作为第一版数据来源，因为它们已经具备互联网资产测绘、被动发现和检索能力。

| 服务 | 适用价值 | 第一版定位 |
| --- | --- | --- |
| FOFA | 国内与亚太客户常用的网络空间测绘服务，适合域名、IP、标题、组件、端口等查询 | MVP 主连接器 |
| Shodan | 国际化设备、服务和主机暴露查询能力强 | 第二阶段候选 |
| Censys | 证书、主机和互联网资产数据结构化程度较高 | 第二阶段候选 |
| ZoomEye | 网络空间搜索与测绘能力，适合作为补充来源 | 候选 |
| 360 Quake / 鹰图 | 国内网络空间测绘来源，可作为内地区域扩展 | 候选 |

FOFA 有公开 API Reference，Shodan 提供 REST API 文档，Censys 提供 Search API 文档，均适合通过连接器方式接入。第一版建议只强制验证 FOFA，避免过早承担多供应商字段差异、配额差异和成本复杂度。

## 5. 商业可行性

该模块适合以“安全工具箱”的增值能力出售：

- 对中小组织，报告比原始资产清单更容易体现价值。
- 对 IT 人员不足的客户，减少从零使用 FOFA/Shodan 查询语法的门槛。
- 对渠道和售前，管理者报告可作为安全现状沟通材料。
- 对续费，历史快照和暴露面变化可以形成持续价值。

商业风险主要来自外部 SaaS 成本和结果质量。必须在产品上设置租户配额、查询预算、缓存策略和报告免责声明。

## 6. 技术可行性

技术上可行，推荐采用“网关 + 连接器 + 归一化 + 报告”的架构：

- 安全工具箱只调用自研网关，不直接保存外部 SaaS 密钥。
- 每个 SaaS 独立连接器适配认证、查询语法、分页、限速、错误码和字段映射。
- 网关统一输出资产、暴露服务、风险线索和报告结构。
- 本地安全工具箱负责后续验证、扫描、巡检和整改闭环。

关键技术难点：

- 不同 SaaS 查询语法不一致。
- 返回字段和数据新鲜度不一致。
- SaaS 额度、限速、失败策略不一致。
- 资产归属存在误报，必须设计置信度和证据链。
- 管理者报告需要降噪，不能只是资产表。

## 7. 合规与安全风险

主要风险包括：

- **数据最小化风险**：客户组织名、域名、IP 段等信息可能具有敏感性。
- **跨区域风险**：香港客户、内地客户和非核心政府单位对数据流向要求不同。
- **供应商风险**：外部 SaaS 可能在境外或跨区域处理查询。
- **滥用风险**：平台可能被用于查询非授权目标。
- **误报风险**：被动数据不等于客户真实资产，需要标注置信度。

缓解策略：

- 网关默认只保存短期快照和脱敏结果。
- 所有任务记录租户、操作者、查询目的、授权范围和来源。
- 对查询目标做组织归属校验和速率限制。
- 管理者报告明确“被动发现结果需要本地验证”。
- 双区域部署：香港区域与内地区域分开承载，数据、密钥、日志和供应商配置隔离。

## 8. 成本与配额风险

成本主要来自外部 SaaS API 调用、报告生成、任务快照存储和运维。

必须在 MVP 中设计：

- 租户级每日/月度查询额度。
- 单任务最大种子数、最大页数和最大结果数。
- FOFA 额度消耗预估。
- 查询缓存，避免重复消耗。
- 失败重试上限。
- 管理后台查看供应商额度与调用异常。

第一版不建议开放任意高级查询语法给客户直接输入，应使用受控的查询模板。

## 9. 推荐路线

推荐路线：

1. 第一阶段：完成需求、架构、数据模型、安全合规和 PoC 计划文档。
2. 第二阶段：实现 FOFA 单连接器 PoC。
3. 第三阶段：形成管理者报告 MVP。
4. 第四阶段：引入第二供应商，优先评估 Censys 或 Shodan。
5. 第五阶段：引入历史趋势、变更告警和本地处置任务联动。

## 10. MVP 建议

MVP 只包含：

- 输入组织名、根域名、IP 段。
- 创建发现任务。
- FOFA 查询规划与调用。
- 资产和暴露服务归一化。
- 简单去重与置信度标注。
- 管理者报告草稿。
- 技术附录资产清单。
- 审计日志与短期任务快照。

MVP 不包含：

- 云端主动扫描。
- 云端漏洞验证。
- 自动渗透测试。
- 复杂攻击面路径分析。
- 多供应商强一致聚合。

## 11. 当前假设

- 第一版主要服务管理者报告。
- FOFA 是唯一必做 PoC 连接器。
- 网关保存短期快照和脱敏结果。
- 安全工具箱本地负责扫描、验证和处置。
- 双区域部署只在设计层锁定，PoC 可先选择一个区域实际落地。
