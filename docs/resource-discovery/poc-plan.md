# FOFA 资源发现 PoC 计划

## 1. PoC 目标

PoC 目标是验证互联网暴露面资源发现模块的最小主链路：

```text
输入资产种子
-> 创建发现任务
-> 查询规划
-> FOFA 调用
-> 结果归一化
-> 去重与风险线索
-> 管理者报告草稿
```

PoC 不追求完整产品 UI，也不接入多个 SaaS。重点验证数据能否被稳定获取、归一化、解释和报告化。

## 2. PoC 范围

PoC 包含：

- 根域名输入。
- 组织名输入。
- IP 段输入。
- FOFA 查询计划生成。
- FOFA API 调用。
- 分页和限速处理。
- 结果字段映射。
- 资产和服务去重。
- 远程访问、管理后台、测试环境等基础风险线索。
- 管理者报告草稿。
- 技术附录资产清单。
- 失败原因记录。

PoC 不包含：

- 云端主动扫描。
- 漏洞验证。
- 弱口令验证。
- 多供应商并行查询。
- 完整权限系统。
- 完整管理后台。
- 正式计费系统。

## 3. 首选 SaaS 连接器

首选 FOFA。

理由：

- 与目标客户区域更匹配。
- 适合验证域名、IP、端口、标题、组件等基础暴露面数据。
- API 接入复杂度适中。
- 能较快验证管理者报告所需的证据链。

第二供应商不进入首个 PoC 必做范围。

后续候选：

- Censys：适合补充证书和国际主机视角。
- Shodan：适合补充设备和服务暴露视角。
- ZoomEye：适合作为另一类网络空间测绘补充。
- 360 Quake / 鹰图：适合内地区域国产供应商补充。

## 4. PoC 数据流

1. 准备测试租户和测试操作者。
2. 输入测试资产种子。
3. 生成 `DiscoveryTask`。
4. 根据种子生成 `SourceQueryPlan`。
5. FOFA 连接器执行查询。
6. 保存脱敏来源证据。
7. 归一化为 `DiscoveredAsset` 和 `ExposedService`。
8. 使用去重键合并重复结果。
9. 生成 `RiskHint`。
10. 生成 `ExposureReport` 草稿。
11. 输出 PoC 验证结果。

## 5. 测试输入样例

测试输入应使用已授权或内部测试目标，不使用未授权第三方目标。

样例结构：

```json
{
  "tenant_id": "tenant_poc",
  "operator_id": "user_poc",
  "region": "hk",
  "purpose": "poc_exposure_review",
  "language": "zh-CN",
  "seeds": [
    {
      "type": "root_domain",
      "value": "example.org",
      "authorization_note": "PoC authorized test domain"
    },
    {
      "type": "organization_name",
      "value": "Example Organization",
      "authorization_note": "PoC authorized organization name"
    },
    {
      "type": "ip_cidr",
      "value": "203.0.113.0/24",
      "authorization_note": "Documentation IP range for structure validation"
    }
  ]
}
```

注意：真实 PoC 执行前必须替换为客户授权范围内的测试目标。

## 6. 验证指标

### 6.1 查询能力

- 能根据根域名生成 FOFA 查询。
- 能根据组织名生成 FOFA 查询。
- 能根据 IP 段生成 FOFA 查询。
- 能记录实际 `source_query`。
- 能处理分页、限速和失败。

### 6.2 归一化能力

- 至少映射 IP、域名、端口、协议、标题、服务、产品、证书字段中的可用部分。
- 每条结果都保留 `source` 和 `raw_reference`。
- 结果能转为统一资产和暴露服务模型。

### 6.3 去重能力

- 相同 `domain_or_ip + port + protocol + service` 合并为一条服务。
- 合并后保留多个来源证据。
- 冲突字段不覆盖证据来源。

### 6.4 报告能力

- 能生成管理者摘要。
- 能列出高风险线索。
- 能给出处置建议。
- 能生成技术附录资产清单。
- 能说明数据来源和局限性。

## 7. 成功标准

PoC 成功标准：

- 能完成至少 1 个根域名任务的端到端流程。
- 能完成至少 1 个组织名任务的端到端流程。
- FOFA 失败时能返回明确错误或部分成功状态。
- 每条高风险线索都有证据摘要。
- 管理者摘要能在非技术读者层面解释主要风险。
- 技术附录能支持 IT 管理员复核。
- 没有云端主动扫描行为。
- 没有保存 SaaS 密钥或完整原始响应到普通日志。

## 8. 风险和备选方案

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| FOFA 配额不足 | 任务失败或结果不完整 | 限制页数、缓存查询、显示部分成功 |
| 查询结果误报 | 报告可信度下降 | 引入置信度和人工确认状态 |
| 组织名查询噪声高 | 资产归属不清 | 根域名和 IP 段优先，组织名结果放入待复核 |
| SaaS API 变更 | 连接器异常 | 连接器隔离，错误码监控 |
| 跨区域疑虑 | 客户无法接受 | 支持香港和内地区域独立配置 |
| 管理者报告过技术化 | 决策价值不足 | 先摘要后证据，技术细节进入附录 |

## 9. PoC 交付物

PoC 完成后应输出：

- FOFA 连接器验证记录。
- 查询样例和字段映射说明。
- 归一化结果样例。
- 风险线索样例。
- 管理者报告草稿。
- 失败和异常清单。
- 是否进入 MVP 实现的建议。

## 10. 进入 MVP 的判断

满足以下条件再进入 MVP：

- FOFA 查询链路稳定。
- 字段足够支撑管理者报告。
- 误报可以通过置信度和待复核状态控制。
- 配额成本可估算。
- 客户愿意接受被动发现和本地验证的产品边界。
- 双区域合规说明没有明显阻断点。
